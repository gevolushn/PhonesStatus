# CLAUDE.md — PhonesStatus

> Інструкція для Claude Code (Desktop і VS Code). Читається автоматично при відкритті проєкту.
> Проєкт створено на основі універсального Python Desktop App Template.

---

## Проєкт

- **Назва:** PhonesStatus
- **Версія:** 1.1.0
- **Опис:** порівнює статуси внутрішніх телефонів між таблицею Excel і поточним станом
  FreePBX (вставленими списками Online/Offline) і показує, які номери підключились,
  а які відключились.
- **Стек:** Python 3.13 + CustomTkinter + PyInstaller (Windows-only)

Уся ідентичність — у `core/build_info.py` (`APP_NAME`, `APP_VERSION`, `GITHUB_REPO`,
`GITHUB_PRIVATE`, `GITHUB_TOKEN`, `TEMP_PREFIX`, `TEMPLATE_VERSION`). Похідні (`APP_MUTEX`,
`SECRET_KEY`) обчислюються з них — не дублювати. `TEMPLATE_VERSION` — база шаблону для
оновлень ядра (див. розділ «Оновлення від шаблону»).

## Доменні знання (не виводяться з коду з першого погляду)

### Формат таблиці Excel (`parsers/xlsx_parser.py`)

- Аркуш обирається за назвою: береться той, у назві якого є **«телефон»** (case-insensitive),
  з виключеннями `старий`, `copy of`, `експорт`. Якщо кандидатів кілька — береться
  **останній** у порядку аркушів (він найновіший). Якщо жодного — активний аркуш + `warning` у лог.
- **Колонка B** (індекс 1) — внутрішній номер. **Колонка H** (індекс 7) — статус.
- Номер нормалізується через `str(int(float(...)))` — щоб `1026.0` з Excel став `1026`.
  Приймаються лише номери з **3–5 цифр** (`^\d{3,5}$`), решта рядків тихо пропускаються.
- Статус приймається лише `ON` або `OFF` (після `.strip().upper()`); інші значення —
  рядок пропускається. Тобто в підсумку в словнику лише валідні пари.
- Рядки, коротші за 8 колонок, пропускаються.

### Формат вставки з FreePBX (`parse_text_block`)

Приймає як таблицю (`PJSIP  1001  0`), так і голий список номерів. Рядок ріжеться по
пробілах, і береться **перший токен, який ЦІЛКОМ складається з 3–5 цифр**; решта рядка
ігнорується. Результат — множина (дублі зникають).

⚠️ Наслідок, перевірений на практиці: номер, «вклеєний» у більший токен, **не** розпізнається —
`SIP/1005-00001` пропускається, бо токен не є чистим числом. Так само відкидаються `12`
(закоротко) і `123456` (задовго). Якщо колись знадобиться підтримка формату `SIP/xxxx-...`,
це свідома зміна регексу в `parsers/xlsx_parser.py`, а не «виправлення бага».

### Правило порівняння (`parsers/comparator.py`)

- Статуси FreePBX збираються у словник: спершу всі `online` → `ON`, потім усі `offline` → `OFF`,
  тож **при дублі в обох блоках перемагає OFF**.
- Порівнюються лише номери, присутні **в обох** джерелах (`xlsx ∩ pbx`).
- У звіт потрапляють лише ті, де статус **відрізняється**; сортування — за номером як числом.
- Формат зміни: `{'num': '1026', 'old': 'OFF', 'new': 'ON'}`.

### Формат звіту (`formatters/result_formatter.py`)

Два представлення того самого звіту: кольорові сегменти `(текст, тег)` для GUI та плаский
текст для `.txt`. Теги (`dim`/`accent`/`green`/`red`/`yellow`/`bold`) — імена; кольори
зіставляє `app_window._apply_result_tags` з палітри поточної теми. Ширина рамок — 52 символи.
У кольоровій таблиці спершу йдуть ті, хто підключився (↑), потім хто відключився (↓).

## Оновлення від шаблону

Проєкт побудовано на версії шаблону `core/build_info.py → TEMPLATE_VERSION` (**2.3.2**).
Щоб підтягти нові фічі/виправлення ядра з новішої версії шаблону:

1. Звір свою `TEMPLATE_VERSION` з останнім релізом шаблону.
2. Відкрий у **репо шаблону** `docs/HOW_UPDATE_YOUR_PROJECT.md` (цей файл у проєкт не їде) —
   Частина I містить процедуру, Частина II — таблиці файлів від твоєї версії до цільової.
3. Оновлюй **вибірково за статусами** (✅/⚠️/🔒/🆕) в окремій гілці, не наосліп — щоб не
   зруйнувати свої кастомізації. Після злиття — онови `TEMPLATE_VERSION`.

### Свідомі відхилення від skeleton (при оновленні НЕ затирати)

| Файл | Відхилення | Чому |
|---|---|---|
| `core/config_manager.py` | `remember = True` (шаблон: `False`) | режим «без слідів» стирав би `xlsx_path` і геометрію щоразу |
| `core/config_manager.py` | `check_updates = False` | GitHub-релізів ще немає; вмикається одним рядком |
| `core/config_manager.py` | ключі `xlsx_path`, `window_geometry` | стан програми між сесіями |
| `gui/widgets.py` | `STATUS_COLORS` + проєктні `build_*` | палітра шаблону не описує акценти ON/OFF/попередження |
| `gui/app_window.py` | повністю проєктний | завжди кастомний файл (🔒 skip у таблицях оновлення) |
| `.gitignore` | `/temp/` і `/exports/` замість `temp/`, `exports/` | шаблон без провідного слеша ігнорує теку на **будь-якому** рівні вкладеності — на першій міграції цим мовчки викинуло `assets/video/` з репозиторію (пункт у `docs/BACKLOG.md` шаблону) |
| немає `build_installed.spec` | обрано лише portable | installed-версія не планується; spec завжди можна взяти з шаблону |

> Не плутати із **системою оновлень продукту** (`updater.py`) — то авто-заміна `.exe` для
> кінцевого користувача, а не синхронізація коду з шаблоном.

### Відома вада ядра, успадкована від шаблону

`core/paths.py` скопійовано зі skeleton **без змін**. У onefile-збірці PyInstaller розпаковує
`assets/` у `sys._MEIPASS`, а `paths.assets_dir()` шукає їх поруч із `.exe` — тож у зібраному
portable `.exe` акцентна тема `neutral.json` не знайдеться (тихий фолбек на CTk `"blue"`,
лише `log.warning`), а `updater.exe` не витягнеться. У dev-режимі проблеми немає.
Рецепт виправлення (`resource_dir()` / `bundled_assets_dir()`) — у `docs/BACKLOG.md` шаблону.
Застосовувати, коли дійде до першої portable-збірки.

## Стиль коду

- Коментарі й docstrings — **українська**; назви змінних/функцій/класів — **англійська**.
- Type hints для публічних функцій; docstrings для публічних функцій і класів.
- Логування — тільки через `from core.logger import log`. `try/except` з `log.error(...)`,
  ніколи мовчазний `pass`.
- Імпорти — абсолютні (`from core.logger import log`).

## Правила роботи

### Версія та git status

На початку сесії і перед будь-яким версійним рішенням — виконати `git status`:
- Порівняти `APP_VERSION` у `core/build_info.py` з останнім комітом / тегом.
- Якщо версія в файлах **новіша** за коміт → запитати: «накопичуємо далі в X.X.X
  чи створюємо нову версію?»
- Якщо версія **збігається** з комітом → запитати: «яка версія для нових змін?»
- **Ніколи не вирішувати номер версії самостійно** — тільки пропонувати і чекати підтвердження.

### Перед зміною коду
- Прочитай відповідний файл перед пропозицією змін.
- Не переписуй те, що працює, без явної причини.
- Зміна кількох файлів — запитай, чи робити все одразу.
- Показуй повний новий варіант функції/файлу; після змін — вкажи, що ще оновити (CHANGELOG тощо).

### Домен
- **Алгоритми `parsers/` не змінювати без явного запиту** — формати Excel і FreePBX описані
  вище й перевірені на реальних даних. Зміна регексів чи вибору аркуша — окреме рішення.
- Формат звіту живе в `formatters/result_formatter.py`, не в GUI. Нове представлення —
  ще одна функція там, а не `insert()` у вікні.

### Event Bus
- Нові міжмодульні комунікації — через `core.events`, не прямі імпорти.
- Імена подій — константи з класу `Events` (не «голі» рядки).
- Підписуй **методи** (`self._on_x`), не голі лямбди (WeakMethod збере їх одразу).
  `unsubscribe` у `destroy()` — бажано.

### Тема
- `ThemeManager` НЕ зберігає конфіг — лише `emit(Events.THEME_CHANGED)`. Персистентність і
  застосування палітри до вікна — у `app_window._on_theme_changed` / `_apply_palette`.
- Віджети головної області створюй через фабрики `make_*` у `widgets.py` (інваріант Gray).
- Акценти ON/OFF беруться з `widgets.STATUS_COLORS` за resolved-режимом теми, не хардкодяться
  у вікні (у світлій темі One Dark-кольори нечитабельні).

### Система оновлень
- Версія — тільки в `core/build_info.py` (`APP_VERSION`).
- `DISTRIBUTION` підміняється spec-файлами (через `core/_build_dist.py`), не вручну.
- `TEMP_PREFIX` узгоджений у `build_info.py` і `assets/updater/updater_src.py` (`phonesstatus_`).
- `GITHUB_TOKEN` — лише fine-grained PAT `Contents:Read-only` на одному репо.
- Перед першою portable-збіркою — зібрати `assets/updater/updater.exe` (див. нижче).
- При релізі: оновити `APP_VERSION` → зібрати → завантажити .exe на GitHub Releases.

### Що НЕ робити
- Не додавати зовнішні pip-залежності без обговорення.
- Не ускладнювати `core/` — він має лишатись мінімальним; проєктна логіка йде у
  `parsers/` / `formatters/`.
- Не пропонувати кросплатформенні рішення (Windows-only).
- Не змінювати `core/events.py` без вагомої причини.
- Не використовувати `grab_set()` у `UpdateDialog`.

## Відомі рішення — не чіпати без причини (стислий список)

- `_mutex` тримається у змінній в `main()` (GC не збирає handle).
- `threading.Thread + self.after(0, ...)` — єдиний безпечний місток у GUI-потік.
- `save_config` — tmp + fsync + `os.replace` (атомарний запис).
- `updater.exe` — окремий stdlib-only бінарник (Windows не дає перезаписати запущений .exe).
- ThemeManager НЕ пише конфіг (Варіант B); палітру до вікна застосовує підписник.
- Приватний asset — `asset["url"]` + octet-stream + ручний 302-редірект.
- `AppContextMenu` тримає одне `tk.Menu` (інакше кожен ПКМ-клік накопичує віджет).

`destroy()` · нова подія — константа в `core/events.py` · нова залежність — у `requirements.txt`.

## Опційні модулі

`optional_modules/` містить готові модулі (crypto, health, state_manager, env_loader,
tray, dialogs, progress, splash). Підключити = скопіювати файл у `core/` чи `gui/` +
додати залежності + інтегрувати за сніпетом (`optional_modules/README_OPTIONAL_MODULES.md`).

**Найближчий кандидат для цього проєкту** — `gui/progress.py` (`BackgroundTask`): читання
великого `.xlsx` зараз відбувається синхронно в GUI-потоці й на великій таблиці підморожує
вікно. Свідомо не підключено при міграції, щоб не міняти потік виконання.

## Git і реліз

Робочий процес: перед комітом — `git status`, показ змін, **автоматична пропозиція labels**
на основі префіксу, очікування затвердження. Коміти та пуш виконуються з дозволу
користувача — в Claude Code (Bash) або вручну у VS Code.

**Префікси комітів та labels:** `init:` · `feat:` · `fix:` · `ui:` · `refactor:` ·
`config:` · `docs:` · `build:`
**Labels за шаром:** `layer: core` (🔴) · `layer: gui` (🟡) · `layer: docs` (🟢)
**Особливі** (за потреби): `breaking-change`, `backlog`.

Реліз: оновити `APP_VERSION`, annotated-тег **без префіксу** `X.Y.Z` (не `vX.Y.Z` —
збігається з `APP_VERSION` буква-в-букву; `updater.py` читає `tag_name` з GitHub Releases),
push тегів у обидва remote (`--tags`), зібрати й завантажити `*_portable.exe` на GitHub Releases.

**Подвійний push** — кожен push двома командами:
```
git push origin main    ← GitHub
git push backup main    ← локальний bare-репозиторій у ~ BACKUP ~
```

## ⚙️ Старт проєкту — збірка updater.exe (виконати ОДИН раз)

Потрібно **перед першою portable-збіркою** (`build_portable.spec` вкладає цей файл у `.exe`):

```bash
cd assets/updater
pyinstaller --onefile --noconsole --name updater updater_src.py
cp dist/updater.exe updater.exe
rm -rf dist build __pycache__ updater.spec
```

Після цього **не чіпай** ні `updater_src.py`, ні `updater.exe` — вважай обидва
замороженими. Перезбирати лише якщо свідомо змінюється логіка апдейтера.
`updater.exe` версіонується у Git проєкту (у `.gitignore` ігноруються лише
`assets/updater/build/`, `dist/`, `updater.spec`).
